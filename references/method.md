# 为什么这么设计

这套东西不是从头想的。一半来自对 `vercel-labs/agent-desktop` 的逆向，
一半来自自己在微信、抖音上返工出来的疤。这份文件记的是取舍，方便以后改之前先看一眼代价。

## 1. 抄了什么

### 证据三态

它的原话是：把三态压成 `bool` 的谓词「只在肯定位安全，一取反就失效」。
我们原来是 `err == 0 ? 值 : None`，也就是把「读不出」和「确定没有」折叠成同一个结果。

真实后果：`AXEnabled` 读失败 → 默认 false → 界面上明明是亮的按钮，被标成 disabled → 换个路子绕，
绕过去就点错。这类错不会报错，只会「偶尔不对」。

现在 `unknown` 是独立状态，且永不取反。代价是多一个字段、多一点判断，收益是「不确定」不再偷偷变成「确定」。

### ref 的捕获证明

它要求整窗完整遍历、谓词整窗唯一、记录字段全部读到，才发 ref；用的时候反向再数一遍。

我们只抄了前三条件（发证），用的时候默认做**轻量复核**（pid + 身份 + 是否还挂在同一窗口，约 1 ms），
`--strict` 才整窗重数。理由是：它那边有 `axtok1:` 元素地址可直达，重数一次的开销相对可控；
我们这边整窗重数在访达上要 7~9 秒，不能默认做。

**代价写在脸上**：轻量复核挡得住「元素消失、窗口换了、身份变了」，挡不住「同身份元素数量变化」。
所以不可逆的写操作请显式加 `--strict`。

### 在哪一处主动偏离了它

它把「字段全读到」当成发证的硬门槛，读不全就一个令牌不给。我们把它拆成两档：

| 档 | 条件 | 放行 |
|---|---|---|
| 完整 | 完整遍历 + 唯一 + 字段全读到 | 全部动作 |
| 受限 | 完整遍历 + 唯一 + **有** `AXIdentifier`，但字段有 unknown | 只放 `setvalue` / `read` |

理由不是宽容，是风险模型本来就不同。点击要靠几何落点，身份读不全意味着「我不确定这是不是我以为的那个元素」，点下去可能打到别人身上；而 `AXSetValue` 直接作用于该元素的属性，不经坐标、不看可见性、不受遮挡影响——它唯一依赖的是「这个元素对象还是它」。后者已由唯一性证明和轻量复核覆盖。

反面证据来自实测：TextEdit 的文档区在空状态下 `AXDescription` 读作 unknown，按老口径拿不到任何令牌，只能退回 `shot` + `tap` 按坐标点进去再粘贴。那条路既慢又真的容易打偏——用严格性换来的不是安全，是更差的替代方案。

所以门禁的实质从「读全才给权限」变成「按动作类型的风险给权限」。

### 投递语义

`delivered` / `not_delivered` / `uncertain` 三态，独立于 `retry: safe|unsafe`。

我们原来 click 返回 `ok: true`。上层一旦超时重试就会点两下 —— 抖音的转发、朋友圈的点赞，
点两下的后果是实打实的。现在坐标点击一律报 `uncertain + unsafe`，让上层必须复核而不是重放。

### 观测与呈现分离

它的 skeleton / 默认 / drill 共用同一个 `snapshot_id`，一次遍历多种投影。

我们落了两个：`--depth N` 只摸结构（不发证），`--from <handle>` 从某个位置继续钻。
慢树上这个区别很关键：访达整窗 7~9 秒，`--depth 3` 只要 70 ms。

## 2. 没抄什么

### 不重写实现

它的 Rust 版在 Mac 上 `batch` 是 28 ms/op，我们自己 15.2 ms/op。重写成 Rust 没有收益，
反而丢掉已经调通的自绘界面通道（它读微信只读到 6 个节点，一步都走不了）。

### 不做「纯语义路线」

它假设界面都有结构。微信 4.x 的整窗只有窗口框 + 3 个无名按钮，
`complete: true` 却什么都读不到 —— 它自己也承认这种情况没办法。

我们保留视觉通道（截图 + 窗口相对坐标 + 剪贴板），并把它写进判定：
`look` 判为 `visual` 就走那条。这是它能做而我们上一轮真机跑通了的那部分。

### 不用它的 full-recursive 遍历策略当默认

Windows/Linux 上它每次操作都要重走整窗（没有元素地址直达）。
我们在 macOS 上保留 AX 元素句柄（注册表），所以 ref 是 O(1) 的，跨进程也能用 —— 只要没重新快照。

## 3. 自己踩出来的

| 疤 | 现在的做法 |
|---|---|
| 照抄截图坐标点错 3 次（图被缩放 1.4 倍） | `tap` 用窗口内点数，坐标由窗口几何现算，根本不看图 |
| 微信搜索框打不进中文（Qt 忽略 unicode 注入） | 写文字一律 `paste`；原生输入框才用 `fill`（AX 设值） |
| 截到纯白图（同进程有幽灵窗口） | 优先筛 `onscreen=true` 且标题非空的窗口 |
| 点「••」误开媒体查看器 | 小区域 `screencapture -R` 换算，或直接量窗口内点数 |
| 同名元素点错 | 发证前整窗数身份；不唯一就扣证 |
| 一次留下 13 个 daemon 孤儿进程 | flock 独占租约，拿不到锁就退让；socket 由持锁者独有 |
| `stop` 杀不掉 daemon | 补上 `shutdown` 分支（原来只在客户端删 socket 文件，进程还在） |
| 一条 `pipe` 长连接堵死所有客户端 | 每连接一个线程，主线程只 accept |

## 4. 代价清单

改之前先看这张表，确认你愿意付。

| 决定 | 付了什么 | 换到了什么 |
|---|---|---|
| 整窗完整遍历才发证 | 慢树一次 7~9 秒（访达） | 「唯一」是真数出来的，不是「我没看到第二个」 |
| 一次遍历读全字段 | 每节点约 10 次 IPC | 渲染时不再回头读，结论与快照绑定 |
| `--strict` 整窗重数 | 几十毫秒到数秒 | 写操作不会因为数量变化点错 |
| 坐标点击报 uncertain | 上层必须复核 | 不会在超时重试时点两下 |
| 网页动作两个进程 | 约 100 ms | ref 指错元素时能发现并改按身份定位 |
| 句柄与令牌分离 | 多一个字段、多一个错误码 | 「看过」和「点得」不再是同一件事 |

## 5. 实测（2026-11-15，macOS 26.5.1 / M4 / 16 GB）

| 场景 | 结果 |
|---|---|
| 计算器整数窗（37 节点） | 75~130 ms，发证 28/29 |
| Chrome 窗口（789 访问 / 490 保留） | 145 ms，发证 376，扣证 114（同名导航项） |
| 微信（6 节点） | 12 ms，判 `visual`，发证 0 |
| 访达·下载（205 节点） | 7~9 秒（每属性往返约 36 ms，AX 固有） |
| 访达 `--depth 3` | 67~73 ms |
| AXPress 回执 | 96~123 ms（`delivered`，应用确认） |
| CGEvent 点击 | 12~25 ms，回执 `uncertain` |
| 混排 11 步（5 桌面点击 + 3 网页动作） | 2.26 秒 |
| 并发冷启动 8 个 daemon | 1 个存活，7 个退让 |

## 6. 还没做

- `AXObserver` 真事件订阅（现在是 10 ms 轮询）
- 多显示器逐屏坐标换算
- 网页侧的「选择器唯一性证明」没有桌面那样严格的计数，只依赖 `querySelectorAll` 命中数
- 慢树的并行遍历（AX IPC 是串行同步的，理论上可以按子树并发，但会打乱唯一性计数）

## 7. 跨平台：Windows 那一半的四个决定

macOS 的实现是 Swift 常驻进程，Windows 这半边不能照抄——Swift 在 Windows 上不是可选项，
而让使用者为了跑一个技能去装编译器和 .NET SDK，等于把这个技能的门槛抬到没人会跨。

### 用 PowerShell，而不是编译一个 exe

Windows 10/11 自带 Windows PowerShell 5.1，也自带 .NET Framework 的 UIAutomation 和
System.Drawing。这意味着：**clone 下来就能跑，零安装、零构建**。代价有两项，都认了：

- 首启动要 `Add-Type` 现场编译约 1~2 秒（常驻进程摊掉，只在第一次付）。
- 只能用 PS 5.1 的 C# 5 内联编译器，不能用 `string interpolation`、`nameof`、
  `?.` 这些新语法。写起来别扭，但换来「不用装东西」。

试过 `csc.exe` 编独立 exe：能被杀软拦、要管 exe 落地与清理、调试链路更长，
而收益只是首启动快 1 秒。不划算。

### 用回环 TCP，而不是命名管道

Python 对 `\\.\pipe\` 的读写没有消息边界语义，也没有可靠的 `select`；而回环 TCP 两端都是
标准流，协议代码可以一字不改地复用 macOS 那套 JSON-lines。

代价是**本机任何进程都能尝试连接**，所以补了两道：32 字节随机令牌（`RandomNumberGenerator`，
不是 `Get-Random`），以及端点文件只对当前用户可读（`icacls` 去掉继承）。令牌放在
`%LOCALAPPDATA%\surehand\wccd.json`，无 BOM 的 UTF-8——带 BOM 会让 Python 的 `json.loads` 直接失败。

### 保留两套角色名，不做统一

UIA 的 `Edit` 与 AX 的 `AXTextField` 是同一个概念，但 UIA 的 `Text` 与 AX 的 `AXStaticText`
又不是字面对应，`Hyperlink` 对应 `AXLink`。**强行统一成一套名字，会在某个平台上制造
一个不存在的名字**。所以：协议层各用各的真名，翻译放在客户端，`--role` 两种写法都收。

### 单线程串行

UIA 客户端本来就该串行调用（COM 单元与跨进程调用顺序都有讲究），所以 Windows 引擎
不做每连接一线程，而是「非阻塞轮询轮转」：一条空闲连接不许堵死别人，但处理仍然是串行的。

这个选择的代价如实写在 SKILL.md 的边界里：**一个慢快照会挡住同时进来的其他请求**。
macOS 侧是每连接一线程，没有这个问题——两边的并发模型不同，是各自平台约束的结果，不是疏忽。

### Windows 独占的一个坑：DPI

`SetProcessDpiAwareness(2)` 必须在任何 UIA 调用之前执行。否则在 125%/150% 缩放的机器上，
UIA 报的是逻辑坐标、`SendInput` 吃的是物理坐标，两者差一个缩放因子——**所有点击都会
系统性偏移**，而且偏移量与缩放比例相关，看起来像「有时候准有时候不准」。

这是 Windows 自动化最高频的失败原因，写在这里是因为它不报错、只点错。
